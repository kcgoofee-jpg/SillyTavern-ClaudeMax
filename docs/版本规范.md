# 版本规范

## 产品版本：一个号，一处写

- 面板、代理、启动脚本**一起发布，共用一个版本号**，格式 [SemVer](https://semver.org/lang/zh-CN/) `主.次.修订`。
- 只写在 `package.json`。改版本用 `node scripts/version.mjs 3.1.0`（同时写进 `manifest.json`，酒馆扩展列表显示的就是它）。门控和 CI 用 `node scripts/version.mjs --check` 检查两处一致。代码里不再手写版本号：代理从 `package.json` 读，测试也从 `package.json` 读。

| 位 | 什么时候加 | 例子 |
| --- | --- | --- |
| 主版本 | 安装方式、目录结构、配置文件格式变了，或者老用户要手动做点什么 | 3.0.0：代码搬进 `src/`，版本号改成单一来源 |
| 次版本 | 新功能，老用户什么都不用做 | 按预设切模型、直连模式、全自动同步 |
| 修订号 | 修 bug、改文案、调参数 | 同步误判、提示语 |

历史：1.x 是原作者 LukaTheHero 的版本；2.x（2026-07 → 2026-09）是本仓库独立维护期，一次提交一个次版本，号涨得很快；**3.0.0 起按上表来**，一个次版本可以包含多次提交，攒够一组相关改动再发。

## 发布流程

1. 平时：改动写进 `CHANGELOG.md` 顶部的「未发布」。
2. 发布：`node scripts/version.mjs x.y.z` → 把「未发布」改成 `x.y.z - 日期` → 提交 `release: vx.y.z` → `git tag vx.y.z` → `git push && git push --tags` → 在 GitHub 建 Release，正文用 CHANGELOG 这一节。
3. 代理是常驻进程：更新代码后要「重启酒馆」才生效。面板状态卡和「检查状态」会显示代理实际运行的版本。

## 分支与提交

- `main` 随时可发布；大改（比如目录重组）在单独分支做，门控通过、评审完再合并。
- 提交信息用 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/)：`feat` / `fix` / `perf` / `docs` / `refactor` / `test` / `chore` / `release`，括号里写范围（`panel`、`proxy`、`launcher`、`sync`）。
- 提交前后自动跑门控（`.githooks`，`git config core.hooksPath .githooks` 启用一次）：单元测试、语法、版本一致、密钥扫描。

## 其他东西各有各的版本线

| 东西 | 版本 | 在哪里记 |
| --- | --- | --- |
| 预设（十四行诗3.0-Claude）| `v主.次-线名`，比如 `v2.9-庄园`、`v2.9-通用`；按版本另存，不覆盖旧版 | 预设改动清单（开发目录 `CHANGELOG-十四行诗Claude.md`）；和产品版本无关 |
| 安卓保活模块 | 自己的 SemVer（`module.prop`）| [tt-root-module](https://github.com/kcgoofee-jpg/tt-root-module) 的 CHANGELOG |
| 代理 ↔ 面板接口 | 跟产品版本；接口有不兼容变化时升主版本 | 本仓库 CHANGELOG |
